## What host discovery is

Host discovery answers one question: **which hosts on a network range are alive?** Before you scan ports, you want a short list of targets. Scanning every port on every IP in a `/16` is a waste of time; finding the handful of live hosts first turns a mountain into a list.

In most lab and exam environments you start with a network range (for example `10.10.10.0/24`) and your first job is to map which addresses respond.

## Discovery techniques

There are five practical approaches — ICMP, TCP SYN, TCP ACK, UDP, and ARP — and they work at different layers of the network stack.

### ICMP discovery

The classic approach: send ICMP Echo Requests (ping) to every address in the range. Linux and Windows hosts that do not block ICMP respond, and Nmap reports them as alive.

<CodeBlock
  lang="bash"
  title="ICMP ping sweep"
  code={`nmap -sn 10.10.10.0/24`}
/>

`-sn` means host discovery only — Nmap skips the normal port scan and just reports which hosts are alive. The target argument accepts a single IP, a subnet, or a range of addresses, so the same command adapts to any scope:

<CodeBlock
  lang="bash"
  title="nmap -sn on a single IP, subnet, and range"
  code={`nmap -sn 192.168.1.42          # single IP
nmap -sn 192.168.1.0/24        # subnet
nmap -sn 192.168.1.100-200     # range of addresses`}
/>

By default on a local network, Nmap will actually use ARP for this (see below), and on non-local networks it falls back to ICMP and TCP probes.

The same ping-sweep idea can be done directly with the platform `ping` tool — note the flag difference between operating systems:

<CodeBlock
  lang="bash"
  title="Platform ping syntax"
  code={`ping -c 1 192.168.1.42        # Linux/macOS: -c 1 sends one echo request
ping -n 1 192.168.1.42        # Windows: -n 1 sends one echo request`}
/>

And remember: a missing ICMP reply does **not** prove a host is down. Windows Firewall and network policy commonly block inbound ICMP echo (via `File and Printer Sharing (Echo Request - ICMPv4-In)` rules) while the host runs perfectly fine. That is exactly why the ARP, TCP, and UDP methods below exist — see [When ICMP fails](#when-icmp-fails).

### TCP-based discovery

Modern hosts and firewalls increasingly filter ICMP, which is why TCP probes are the modern default. Nmap's `-sn` automatically sends a SYN packet to port 443 and an ACK packet to port 80 in addition to ICMP; any response marks the host as alive. The probe types below each answer a different firewall scenario.

### TCP SYN discovery (`-PS`)

The default modern probe. Nmap sends an empty TCP SYN packet (a half-open connect) to the listed ports and treats the response as the "alive" signal:

- `SYN/ACK` means the port is **open** → host is alive.
- `RST` means the port is **closed** → host is alive (a real host replies `RST`; only a silent network drop means "no answer").
- No response at all → host did not answer this probe.

Because a single well-chosen port is usually enough, default Nmap behaviour sends SYN to ports 443 and 80 when ICMP is blocked. You can choose your own ports with `-PS`:

<CodeBlock
  lang="bash"
  title="TCP SYN host discovery"
  code={`nmap -sn -PS80,443,22 10.10.10.0/24`}
/>

### TCP ACK discovery (`-PA`)

Some firewalls inspect and drop SYN probes but pass oddball packets. The ACK probe exploits this: since the ACK flag does not belong to any real connection, a firewall that does not track state passes it through, and the host answers with `RST`. Any `RST` = host alive.

<CodeBlock
  lang="bash"
  title="TCP ACK host discovery"
  code={`nmap -sn -PA80 10.10.10.0/24`}
/>

### UDP discovery (`-PU`)

UDP is fire-and-forget: a "response" is an **ICMP port unreachable** message, which is itself generated by a live host. It is slower and noisier than TCP discovery because many firewalls silently drop UDP — but it can be the only thing that reveals a host on a network that filters everything else.

<CodeBlock
  lang="bash"
  title="UDP host discovery via DNS"
  code={`nmap -sn -PU53 10.10.10.0/24`}
/>

### Combining discovery probes

`-sn` is not one technique — it is a mix, and you can combine any of the probes in a single sweep. Each probe type is additive, so the more you add, the fewer hosts you miss:

<CodeBlock
  lang="bash"
  title="Combining TCP probes"
  code={`nmap -sn -PS443 -PA80 192.168.1.0/24`}
/>

A lean common combination: `-PS443` sends a TCP SYN probe to the HTTPS port and `-PA80` sends a TCP ACK probe to HTTP — enough to catch most web-serving hosts even when ICMP is filtered.

You can go further and mix TCP with UDP probes in one sweep:

<CodeBlock
  lang="bash"
  title="Combined TCP and UDP discovery"
  code={`nmap -sn -PS80,443,22 -PA80 -PU53 10.10.10.0/24`}
/>

Here `-PS` sends TCP SYN probes to ports 80, 443 and 22, `-PA` sends a TCP ACK probe to port 80, and `-PU` sends a UDP probe to DNS port 53. Any host that answers **any** of these is reported as alive. This matters when ICMP is blocked but TCP or UDP services respond.

### ARP discovery

On a local network segment, Nmap does something faster and more reliable than any IP-level probe: it uses ARP. Since every alive host on the local segment must respond to ARP to function at all, an ARP request reliably identifies live hosts — and reveals their **MAC addresses**, which is a bonus (see [Network Discovery & ARP](/guides/info-gathering/network-discovery-arp)).

<CodeBlock
  lang="bash"
  title="Forcing ARP discovery on the local network"
  code={`nmap -sn -PR 10.10.10.0/24`}
/>

`-PR` forces ARP ping. Nmap uses ARP automatically when the target is on the same layer-2 segment, so you will usually get this behaviour for free.

## When ICMP fails

ICMP is the first thing many administrators and firewalls filter. Do not assume that a non-responsive host is dead:

- **Firewalls drop ICMP** while leaving TCP services open.
- **Windows hosts** often block inbound ping while running SMB, RDP, or WinRM.
- **Rate limiting and asymmetric routing** can make pings unreliable.
- Some hosts **respond slowly** and get missed during a fast sweep.

This is exactly why Nmap's `-sn` combines ICMP with TCP probes. If you suspect a range is under-reported, repeat discovery with `-PS` ports that match common services:

<CodeBlock
  lang="bash"
  title="Host discovery when ICMP is filtered"
  code={`nmap -sn -PS22,80,443,445,3389 10.10.10.0/24`}
/>

A host that answers a TCP probe on port 445 is alive even if it never answers a ping.

## Ping sweeps with other tools

Nmap is the workhorse, but it is not the only way to sweep a range. Knowing the alternatives helps you pick the right speed for the job, and the concepts carry over to every tool you will meet in the field.

### fping

`fping` is purpose-built for ping sweeps — it sends ICMP echo requests to many hosts in parallel and prints only what answered. Where `ping` waits for one host at a time, `fping` blasts a whole range and collects the replies.

<CodeBlock
  lang="bash"
  title="fping a subnet"
  code={`fping -a -g 192.168.1.0/24 2>/dev/null`}
/>

- `-g` tells fping to sweep the range.
- `-a` shows only **alive** hosts (default output includes everything, alive or not).
- `2>/dev/null` discards error messages (permission errors, unreachable-address warnings) so the output is a clean list of live hosts.
- Combine with `-r 0` to skip retries and speed up dead hosts: `fping -a -g -r 0 192.168.1.0/24 2>/dev/null`.

**Expected result:** one line per responding host (`192.168.1.10 is alive`), and silence for everything else — exactly the target list you want before port scanning.

fping is often installed by default on Linux and macOS systems, making it the fastest way to do a quick sweep without starting Nmap.

### A bash one-liner

No extra tools at all — just the shell and `ping`:

<CodeBlock
  lang="bash"
  title="Bash ping sweep"
  code={`for i in $(seq 1 254); do ping -c 1 -W 1 192.168.1.$i &>/dev/null && echo "192.168.1.$i is alive"; done`}
/>

Run it from a Linux machine and it prints `192.168.1.X is alive` for every host that answered a single echo request. Breaking it down:

- `for i in $(seq 1 254)` — loop over addresses `.1` through `.254` (the usable host range of a `/24`).
- `ping -c 1 -W 1 192.168.1.$i` — send one echo request (`-c 1`) and cap each wait at one second (`-W 1`).
- `&>/dev/null` — discard ping's output and errors; we only care about the exit code.
- `&& echo "..."` — `echo` fires only when `ping` exits successfully, i.e. a host replied.

It is slow and clunky, but it works on a bare system with no tools installed — a useful fallback during an exam or a minimal-box challenge.

## Advanced Nmap discovery

The probe types so far are individual techniques. Nmap lets you stack them, tune the speed, skip DNS, and save output in a single sweep. Three options appear in almost every advanced discovery pass:

- **`-n`** — disables DNS resolution. Nmap does not reverse-resolve every IP, which is faster and quieter, and avoids stalling on networks with broken DNS.
- **`--min-rate 300`** — sets a floor of 300 packets per second, so a sweep over a large range completes much faster than the default timing allows.
- **`-oA full_discovery`** — saves the results in all three output formats (normal, XML, grepable) under the basename `full_discovery`.

In addition to the echo probe, Nmap can use other ICMP packet types that some firewalls pass while filtering echo:

- **`-PE`** — ICMP echo request (the classic ping).
- **`-PP`** — ICMP timestamp request. Some filters allow timestamps while dropping echoes.
- **`-PM`** — ICMP netmask request. The same idea with a different packet type.

## Comprehensive discovery

A full discovery pass stacks everything together — every probe type, no DNS, a fast rate, and saved output:

<CodeBlock
  lang="bash"
  title="Comprehensive host discovery"
  code={`nmap -sn -PE -PP -PM -PS21,22,23,25,80,443,445,3389,8080 -PA80,443 -PU53,161,137 -n --min-rate 300 -oA full_discovery 192.168.1.0/24`}
/>

Option by option:

- **`-sn`** — host discovery only; no port scan.
- **`-PE`** — ICMP echo request probe.
- **`-PP`** — ICMP timestamp request probe.
- **`-PM`** — ICMP netmask request probe.
- **`-PS21,22,23,25,80,443,445,3389,8080`** — TCP SYN probes to a spread of common services (SSH, SMTP, HTTP, SMB, RDP, and more).
- **`-PA80,443`** — TCP ACK probes to the two common web ports.
- **`-PU53,161,137`** — UDP probes to DNS, SNMP, and NetBIOS.
- **`-n`** — skip DNS resolution.
- **`--min-rate 300`** — floor the packet rate at 300 packets per second.
- **`-oA full_discovery`** — save output in all three formats.

**Set your expectations correctly:** stacking more probe types improves coverage, but it does *not* guarantee the best possible results. Hosts and network configurations respond differently — one host may answer an ACK probe while another only answers a UDP probe, so combining them catches a wider variety of hosts. It can still miss a host that drops everything. Aggressive rates also increase traffic: `--min-rate 300` generates far more packets than a default sweep, which is more noticeable (and more detectable) on a busy or monitored network.

## When host discovery should be skipped

There are cases where `-sn` is the wrong tool and you should go straight to port scanning:

- **You already have a target list.** If the scope is "these 20 IPs", just scan them.
- **The range is small.** One or two hosts — just scan them directly.
- **Hosts actively hide.** Hosts that silently drop everything (including TCP) look dead to any probe but may be reachable. This is common in exams designed to test your methodology. If your full TCP scan of a suspicious host shows nothing, it may still be worth a slow full scan.
- **You are scanning a single IP.** `nmap 10.10.10.42` does host discovery and the port scan in one shot.

<Alert variant="warning" title="Do not trust 'host down' blindly">
  Nmap prints <code>Host seems down</code> and skips the port scan when no probe is answered. If you have a reason to believe a host exists, scan it directly anyway: <code>nmap -Pn 10.10.10.42</code> skips host discovery and scans every port. This is one of the most important flags in an exam context.
</Alert>

## Understanding filtered and unreachable hosts

During discovery you will see three categories of behaviour:

| Result | Meaning | What to do |
|---|---|---|
| Responds | Host is alive | Port scan it |
| Silently drops all probes | Could be dead, filtered, or hiding | Try a direct full scan with `-Pn` |
| Returns ICMP unreachable | Host or network is filtering | Note it; usually not worth chasing in a lab |
| Responds but you were not allowed to scan it | Out of scope | Stop immediately, document it |

Note the difference between a host that answers nothing and a host that *actively* refuses. `icmp-host-unreachable` messages from a router can also make Nmap report a host as down even when it is not.

On a typical authorized lab network:

**What the output means:** 3 hosts responded out of 256 addresses. Those three are your targets. (On a local network the "latency" values are near-zero because the replies come from ARP, not ICMP.)

Now port-scan each live host:

<CodeBlock
  lang="bash"
  title="Step 2 — port scan the live hosts"
  code={`nmap -p- 10.10.10.10 10.10.10.11 10.10.10.42`}
/>

## Command reference

| Command | Purpose | Expected result | Investigate next |
|---|---|---|---|
| `nmap -sn 10.10.10.0/24` | Standard host discovery | List of live hosts | Port scan each live host |
| `nmap -sn -PS443 -PA80 RANGE` | Discovery with TCP probes | Live hosts that ICMP misses | Compare with ICMP results |
| `nmap -sn -PR 10.10.10.0/24` | Force ARP discovery (local) | Live hosts + MAC addresses | Cross-check with [Netdiscover](/guides/info-gathering/netdiscover) |
| `nmap -sn -PE -PP -PM -PS... -PA... -PU... -n --min-rate 300 -oA file RANGE` | Comprehensive discovery | Live hosts across all probe types | Port scan the survivors |
| `fping -a -g RANGE 2>/dev/null` | Parallel ping sweep | Clean list of alive hosts | Cross-check with Nmap `-sn` |
| `nmap -Pn 10.10.10.42` | Skip host discovery, scan all ports | Ports even on "hidden" hosts | Enumerate every open port |
| `nmap -sn --open 10.10.10.0/24` | Discovery without omitting hosts | Complete list (includes non-open hosts) | Review which hosts have no open ports |

## Common mistakes

- **Only scanning the top 1000 ports** during follow-up, missing services on higher ports.
- **Believing `Host seems down` is authoritative** without retrying with `-Pn`.
- **Assuming ICMP filtering means a host is dead.**
- **Scanning the whole range with `-sn` and never doing a full TCP scan of the survivors.**
- **Forgetting that ARP works only on your local segment** — `-PR` is useless against remote networks.
- **Treating the comprehensive sweep as proof of absence.** More probe types improve coverage, but a host that drops everything still looks dead; confirm important targets directly with `-Pn`.
