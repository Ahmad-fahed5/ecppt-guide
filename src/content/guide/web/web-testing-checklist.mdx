## How to use this checklist

Work this list for **every web service** you take on in a lab. It is the distilled version of the whole web section — follow the items in order, tick them as you go, and your notes will contain the complete attack surface for the [exploitation](/guides/exploitation) phase.

<Alert variant="info" title="Progress is saved">
  This checklist stores its state <strong>locally in your browser</strong>. Refresh the page and your ticks survive. Use the Reset button to start a fresh web target.
</Alert>

<SourceTag source="practical" /> This is a *working* checklist, not an OWASP compliance sheet. Each item exists because it feeds the next decision in [Web Exploitation Methodology](/guides/web/web-exploitation-methodology).

## What each item really means

- **HTTP/HTTPS identified** — you made an actual request and saw the response, not just an Nmap line.
- **Technology identified** — stack known; drives extension choices and syntax guesses (see [Web Enumeration](/guides/web/web-enumeration)).
- **Headers reviewed** — `Server`/`X-Powered-By` give the stack; security headers tell you hardening posture.
- **Cookies reviewed** — `HttpOnly`/`Secure`/`SameSite` at login shape XSS and CSRF impact (see [Web Fundamentals](/guides/web/web-fundamentals)).
- **robots.txt / sitemap.xml** — free paths; always read before brute-forcing.
- **Virtual hosts tested** — different `Host` values can reveal a different app on the same IP.
- **Directories / files enumerated** — the route map; note status codes for every hit.
- **Parameters identified** — the test targets; without this list the rest of the checklist has nothing to act on.
- **Endpoints discovered** — the JS/forms harvest beyond wordlists.
- **Authentication tested** — login behaviour, not just "it works".
- **Session management tested** — the cookie lifecycle from [Authentication & Authorization](/guides/web/authentication-authorization).
- **Authorization tested** — direct URL access and method changes, not just the UI.
- **IDOR tested** — object ids swept with a second account.
- **SQL injection tested** — manual probes before automation (see [SQL Injection](/guides/web/sql-injection)).
- **File inclusion / upload / command injection / XSS / CSRF tested** — the [vulnerability guides](/guides/web/web-exploitation-methodology) each define the minimal proof.
- **Initial access opportunities reviewed** — everything that could turn a finding into a shell.
- **Findings documented** — exact request + response saved; evidence is the deliverable.
- **Next attack path identified** — the honest answer to "what do I do next".

## Quick command cheat-sheet

<CodeBlock
  lang="bash"
  title="The essentials, in checklist order"
  code={`# 1. Confirm + identify
curl -i http://TARGET
whatweb http://TARGET

# 2. Free intel
curl -s http://TARGET/robots.txt
curl -s http://TARGET/sitemap.xml

# 3. Vhosts
curl -H "Host: candidate" http://TARGET/

# 4. Enumerate
gobuster dir -u http://TARGET -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt -x php,txt,bak
curl -s http://TARGET/ | grep -Eo '(href|action|src)="[^"]*"'

# 5. Probes (one class per confirmed parameter)
# SQLi:      ?id=42'  /  ?id=42 AND 1=2  /  ?id=42 AND SLEEP(5)
# LFI:       ?page=../../../../etc/passwd
# Cmd inject:?host=TARGET; id
# XSS:       ?search=<script>alert(document.domain)</script>
`}
/>

## Common mistakes

- **Ticking an item because you ran a command** — a tick means you *interpreted* the result, not just that you sent it.
- **Skipping parameters and going straight to exploitation** — the checklist only works when the map is complete.
- **Testing one context** for a class (one parameter, one injection type) and calling it covered.
- **Forgetting to capture evidence** — the exact request/response pair per finding.
- **Not ending with the next step** — the checklist's last item decides where the [next phase](/guides/exploitation) starts.
